## Comments (worker, 2026-10-17, COMMIT NOTHING, screening-only — zero new sbatch)

**Bottom line for the conservator:** the flagger never seats a piece itself — it repaints which breakline spans count as rim, and that repainting changes the scores the beam search reads. Think of it as re-marking the "do not match here" zones on a few sherds: every match touching those sherds gets weaker, the search's starting order reshuffles, and the assembly walks into a different valley. On D and I the new valley holds fewer true joins (2–3 sherds lost); on J the reshuffle accidentally clears the traffic jam that had trapped the search, and two sherds click together for the first time. No new compute was spent: everything below is read out of the 15 existing run logs plus the piece-identity recomputation (same script as 61).

**Code mechanism (verified in cure-potA source, read-only):** flipping a segment flag 0→1 does three things at once — (1) `feature_matching.cpp` LCS loop: any cell where either point lies in a flagged span is zeroed (`a_cdt||b_cdt → LCSuff=0`), so recalled spans contribute no match length; (2) `data_structure.cpp` `BuildTree`: flagged spans never enter the KD search tree, so no correspondences are even proposed there; (3) the same flagged points feed `rim_data → H_rim`, which moves the rim veto boundary (`top_gap>0 && bottom_gap>0 → kill`, `feature_matching.cpp:1228-1237`, `ranking_system.cpp:1831-1837 → PC_`). Channels (1)+(2) are directly visible in the logs (forest/pruned/SortRoot deltas); channel (3) changes only graphs containing flagged pieces, and per-edge veto kill counts are NOT printed in BASE logs — naming them needs an instrumented VERBOSE arm (proposed below, not run).
